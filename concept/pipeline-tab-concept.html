Why this feels simpler

The design reduces simultaneous choices without removing capability. All existing pipeline data still has a home; it is just organized by the moment in which a person needs it.

1Structure stays in sight

The left rail is the pipeline’s table of contents. Selection, order, type, and summary are readable without opening and closing five large cards.

2Essentials before edge cases

Name, type, runner, image, and commands lead. Host aliases, artifacts, secrets, and failure behavior sit in scannable disclosure groups.

3Global and local settings separate

Build inputs and pipeline defaults live beside the stage list, clearly outside the selected stage’s inspector.

4Save state never disappears

The sticky command bar communicates revision, validation, dirty state, preview, and the single primary action throughout the edit.

5Type controls the form

Changing a stage type swaps in only fields consumed at runtime. A checkout stage becomes a short explanation instead of an empty technical form.

6Validation happens in context

Stage validity and runner compatibility appear next to the edited configuration, before a user spends a build discovering a typo.

Scope: this concept can reuse the current pipeline payload and single-request save model. The main implementation change is component composition and local selection state; richer preflight validation can ship incrementally.
