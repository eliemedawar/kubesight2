KubeSight · Signal v3 · Concept

One field.
A building service.

Registering a service today asks for a name, a type, a team, a criticality, a repository, a branch, a credential, and a pipeline — eight decisions before the first build. This concept collapses onboarding to one input, the repository URL. Everything else is derived live from the repository itself, shown as an editable proposal, and never asked as a blank field.

Service Catalog / CI replaces the Register-service modal 1 new endpoint, 0 schema changes

Three rules

Ask once The repository URL is the only mandatory question. A credential is asked only if none is stored yet — then never again.
Derive, don't default Name, type, branch, pipeline, working directory come from the repo's own files — each with its evidence shown, each editable inline.
Never block Detection failing or ambiguous never stops creation. The proposal degrades to “Generic” with the choices open — the user is never stuck behind a spinner.

Detection matrix

One tree listing per inspect — the same capped, validated Bitbucket client Application Intelligence already uses for Dockerfile discovery. First match per directory wins, top-down:

Dockerfile alongside any match is additive: it appends the Build Image stage to that type’s pipeline instead of overriding the type.

Backend delta — one endpoint

Everything else already exists: templates per type, credential store, branch listing, registry connections, Run Build. Detection is one new read-only call:

# request — auth: ci_services:create POST /api/ci/source/inspect { "repositoryUrl": "https://bitbucket.org/areeba/payment-service", "credentialProfileId": 3, // omitted → auto-pick "branch": "develop" } // omitted → repo default # response — a proposal, not a decision { "reachable": true, "suggestedName": "Payment Service", "defaultBranch": "develop", "branches": ["develop", "main", "release/1.7", …], "applications": [ // >1 ⇒ monorepo state { "workingDirectory": "", "applicationType": "java", "evidence": [{ "file": "pom.xml", "rule": "maven" }, { "file": "Dockerfile", "rule": "container-image" }], "pipelinePreview": ["Checkout","Build","Unit Tests","Package","Build Image"] } ], "credential": { "id": 3, "name": "bitbucket-ci-read", "autoPicked": true }, "registryConnection": { "id": 1, "name": "nexus-prod", "autoPicked": true } }

Implementation: services/ci/source/inspect.py walking the already-shipped application_intelligence_bitbucket tree client (capped at 5 000 entries, HTTPS-pinned, response-size-limited). “Create & build” then chains the existing POST /services → PUT /source → POST /builds.

Edge cases, decided

SituationBehavior
No credential stored yetInline add-credential row inside the sheet — the one-time exception to “ask once”.
Credential rejected / repo not foundSheet shows the exact error; creation stays possible with source disconnected (today’s two-step flow remains the fallback).
Inspect slower than 3 sProposal card renders in skeleton state; “Create & build” downgrades to “Create only” so the URL is never held hostage.
Ambiguous detection (several rules hit one directory)Highest-precedence rule wins, others listed under “also matched” — one click to switch.
Two stored credentials both workNo auto-pick; the picker opens pre-filtered to the two.
Re-pasting an already-registered repoSheet points at the existing service instead of creating a duplicate.
