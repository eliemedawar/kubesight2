KubeSight · Native CI · Builds tab

UI/UX concept · stage view

Every build, every stage,
one grid.

Jenkins' Stage View answers a question our Builds table cannot: where does this pipeline keep breaking? This is that grid, rebuilt in Signal — and taught the four things our engine knows that Jenkins never did.

Design position

Kept from Jenkins

  • Stages are columns, builds are rows, newest on top. The eye reads a column to judge a stage and a row to judge a build.
  • Every cell is a duration. Time is the number engineers actually compare.
  • Per-stage averages, so a cell reads as fast or slow without arithmetic.
  • The whole recent history on one screen — a pattern needs no drill-down to be seen.

Changed for KubeSight

  • Colour means state, not brand. Signal's red stays on actions and the live rail; a failed cell is danger and a running one info — the same semantics as every status pill in the app.
  • Skipped is neither green nor red. Our engine skips a stage it cannot honestly run and writes down why. Jenkins has no such state, so it would paint a build that produced no image as a success.
  • Not reached ≠ skipped. Stages after a failure go quiet rather than amber — nothing is wrong with them.
  • Cells act. Open the logs at the first error, or rerun the build from that stage. The engine already does both.

Alignment is the hard part

        
A build snapshots its pipeline, so the history holds pipelines that no longer exist. Columns align on stage name, ordered by the newest build's positions; a stage a build never had is drawn as a void rather than a gap. Rename a stage and it becomes a new column — truthful, and visible.

      

      

        
The gutter carries provenance

        
The same vocabulary as the Builds table it toggles with: number, ref (tag chip for a tag build), commit, who or what asked for it, where it landed. A grid of durations that cannot say whose build this was sends people straight back to the table.

      

    

  


  

    
The cell states

    
Ten, and every one is a state the engine can actually produce. Tint, glyph and wording together — never colour alone.

    

  


  

    
Averages live in the header

    

      

        
Not a row of its own

        
Jenkins puts “average stage times” in a row above the builds, where it reads like another build. Here the average belongs to its column: stage name, avg 62s, and a bar for that stage's share of a typical build. The slowest stage in the pipeline then falls out of the bar lengths alone.

      

      

        
Averaged over passes only

        
A stage that fails in 30ms would drag its own average down and make every real run look slow, so averages come from successful runs. A cell above 1.6× its column average gets a ▲ and, in its card, “2.5× slower than usual”. Under three passes there is no average yet and the header says so rather than inventing one.

      

    

  


  

    
Where it lives

    
    
      
  • Builds tab — a Table / Stages segmented control. Stages leads when the pipeline has two or more stages and the service has two or more builds; otherwise the table, because one row of durations is not a grid.
    • 
      
  • Overview keeps its single-build strip. That strip answers “what is happening now”; the matrix answers “what keeps happening”.
    • 
      
  • A cell click never navigates. It pins a card, and the logs open in the pane below — losing the grid to read one stage is what makes Jenkins' view a dead end. The full build drawer stays reachable from the gutter.
    • 
      
  • Density. Gutter and header stay pinned while the grid scrolls sideways on its own; past eight stages the columns shrink to 92px and names truncate, with the full name in the card. The page body never scrolls sideways.
    • 
      
  • Polling keeps the existing rule — 4s while a build is active, nothing once the history has settled. Only the live row changes, so the grid is patched rather than rebuilt.
    • 
    

  


  

    
Keyboard & screen readers

    
    
      
  • A real <table> with scope="col" stage headers and a row header per build, so a screen reader announces “Build Image, build 28: failed, 19 seconds”.
    • 
      
  • Roving tabindex: one stop enters the grid, arrows move within it, Enter pins the card, Esc leaves. Tab does not visit seventy cells.
    • 
      
  • The running cell is an aria-live="polite" region naming its stage and elapsed time — the one thing here that changes without input.
    • 
      
  • Every status carries a glyph and a word, so the grid survives greyscale printing and colour-vision deficiency.
    • 
    

  


  

    
What the backend owes it

    
Rendering this from today's API would cost one request per build. One endpoint instead, because alignment and averaging are set operations over ci_build_stages:

    
GET /api/ci/services/<id>/stage-matrix?limit=12&status=all

{
  "columns": [
    { "key": "build-image", "name": "Build Image", "stageType": "container_image",
      "avgSeconds": 24, "sampleSize": 9, "shareOfBuild": 0.18 }
  ],
  "rows": [
    { …build_summary + automation, exactly as the Builds table gets it…
      "cells": {
        "build-image": { "stageId": 412, "status": "failed", "durationSeconds": 19,
                         "exitCode": 1, "error": "The stage reported failure.",
                         "continueOnFailure": false, "logTail": […3 lines…] }
      } }
  ]
}

    

      

        
FieldWhy the grid needs it

        
          
cells[key] = nullThe build never had that stage — draws the void instead of an empty pass.

          
errorThe engine already writes the skip reason (“This runner cannot build container images…”). It is the entire point of the amber cell.

          
continueOnFailureA red cell in a build that kept going has to say so, or the row reads as a lie.

          
logTailThree lines in the card means most failures get diagnosed without opening anything.

          
avgSeconds, sampleSizeThe header average — and the honesty to hide it under three samples.

        
      

    

    
All of it exists per row already: build_stage_to_dict carries status, duration, exit code and error, and rerun_from(build, position) is the cell's second action. No new columns, no new state.

  


  

    
Build order

    

      
The endpoint. One query for the last N builds, one for their stages, aligned by name in Python, averages from passes only. Tests: a pipeline edited mid-history, a build with one stage, a service with none.

      
The grid, read-only. Table markup, sticky gutter and header, the ten cell states, the header averages. Ships behind the segmented control with Table still the default.

      
The card and its two actions. Log tail, open-at-first-error into the existing viewer, rerun-from-here through rerun_from. Then flip the default to Stages.

      
The verdict line. Worst column by failed + timed out + skipped, said in one sentence and clickable as a filter. Cheap — and it is the reason anyone opens a stage view at all.
