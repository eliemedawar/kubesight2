KubeSight · Signal v3 · UI/UX Concept

The Service Catalog tab:
a build floor, not a list.

With native CI replacing Jenkins, the Service Catalog is where every build in the organisation starts, runs, and hands off to deploy. This concept redesigns the tab around that role: the grid answers "is everything building?" at a glance, a card answers it per service, and everything actionable is one click from where the question arose.

catalog grid + service page + build drawer pairs with the one-field onboarding concept no new backend required for P1

Design position

Four decisions shape everything below — each corrects a real weakness of the current v1 tab:

DecisionCorrects
Health strip with tiles-as-filters — running / failing / queued / needs-setup counts at the top; clicking a tile filters the grid (the proven Alerts pattern). v1 opens on an undifferentiated grid; a failing build looks exactly as loud as a healthy one until you read every card.
The card is a verdict, not a record — one dominant signal (last build outcome), sparkline of the last 10 builds, and a hover-revealed Run action. v1 cards list facts (repo, branch, stages) with equal weight; scanning 30 services means reading 30 cards.
Every incomplete state carries its next action — "Source needed → Connect", "Pipeline needed → Configure", "Runner offline → Enable". v1 shows warning chips but the fix lives two navigations away.
Traceability is a first-class row — commit → build → artifact → deploy rendered as one chain on artifacts and automation-triggered builds. The Jenkins-free promise is invisible unless the UI shows the whole chain happening inside KubeSight.

  1. 1Health strip, tiles are filters. Live counts (4s poll, only while something is active). Clicking FAILING shows the two red cards and nothing else — same mechanics as the Alerts tiles, so it needs no learning.
  2. 2Needs-setup is a first-class state. Half-registered services stop hiding in the grid; the tile collects them for a setup sweep.
  3. 3Verdict line. Outcome + failing stage + recency in one line, and a 10-build sparkline for trend (three reds in the last four ≠ one flake). Clicking the verdict opens the failing build's drawer directly — not the service page.
  4. 4Trigger provenance. Builds started by tickets wear an automation chip; the card shows the org that CI runs itself, no Jenkins.
  5. 5Run from the card (hover/focus-revealed, permission-gated). The most common action must not cost a navigation. Disabled with a tooltip while a build is running at the concurrency cap.
  6. 6Incomplete cards are dashed and their chip is the action — "Connect" deep-links to the Source tab. A dead-end chip is a design bug.

  1. 1Stage rail auto-follows the action: selects the running stage live, lands on the failed one when the build ends. The user's first click is already done for them.
  2. 2Masking is visible, deliberately. Secrets show as *** — evidence that the masker ran, and a reminder that pasting secrets into build output is pointless.
  3. 3"Jump to first error" scans the stored log for the first stderr/ERROR line — the single most repeated manual action in any CI log viewer.

4 · States that must be designed, not defaulted

StateTreatment
Empty catalogThe one-field onboarding sheet inline in the empty state — not a hint pointing at a button somewhere else. First service ≤ 60 seconds.
Build queued with a reasonThe queue reason verbatim where the spinner would be: “Waiting: every runner with macos is at capacity”, with a link to Runners for ci_runners:manage holders.
Stage skipped (BuildKit off, registry unlinked)Dashed pill + the stage log's explanation surfaced as a tooltip. Never rendered as success; never rendered as failure.
Runner fleet downBanner above the grid — a grid of “queued” cards with no explanation reads as a broken product.
Automation build failedThe failure card links both ways: to the build drawer AND to the originating ticket run in Ticketing.

5 · Motion, keyboard, a11y

Motion budget: sparkline bars grow once on load (120ms, opt-out via prefers-reduced-motion); the building-card pill pulses at 2s; nothing else moves. Grid cards are buttons: Enter opens, R runs (with permission), drawer traps focus and restores it on close. Status never rides on colour alone — every state pairs colour with a word or glyph, which is also what makes the dashed/solid card distinction work in both themes.

What this costs the backend: almost nothing. The strip counts come from the existing list endpoints (one aggregate added to GET /api/ci/services); the sparkline is the last 10 build statuses already on the summary; “Jump to first error” is a client-side scan of the log payload; the Deployed column reads application_deployment_versions.ci_build_id, which the CD handoff already writes.
