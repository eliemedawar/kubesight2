## 3. OAuth setup (reuse zagent — server-to-server "Self Client")

> The app acts as **zagent@areeba.com**, so it inherits zagent's Desk permissions. Use a dedicated **Self Client** (server-to-server, no user-login flow) — do NOT reuse the Deluge/MCP connection's tokens. **Never commit the real client_secret / refresh_token to git** — fill the placeholders below only in the secure hand-off copy.
> **Data center:** Areeba is on the **`.com`** DC → console `api-console.zoho.com`, accounts `accounts.zoho.com`. Keep the DC consistent everywhere.

### 3a. Owner creates the client (one-time, in Zoho API Console)
1. Sign in to **`https://api-console.zoho.com`** as **zagent@areeba.com** (the identity the app will act as).
2. **Add Client → Self Client** → Create (or reuse an existing Self Client under zagent).
3. From the **Client Secret** tab, copy **Client ID** and **Client Secret**.
4. **Generate Code** tab:
   - **Scope:** `Desk.settings.READ,Desk.settings.UPDATE`
   - **Time Duration:** 10 minutes · **Scope Description:** `DevOps field sync`
   - Create → copy the **grant code** (valid only for the chosen minutes; single use).
5. Within that window, exchange the code for tokens (run in **your own terminal** — the code + secret are sensitive):
   ```
   curl -X POST "https://accounts.zoho.com/oauth/v2/token" \
     -d "grant_type=authorization_code" \
     -d "client_id=<CLIENT_ID>" \
     -d "client_secret=<CLIENT_SECRET>" \
     -d "code=<GRANT_CODE>"
   ```
   The response contains a long-lived **`refresh_token`** (and a 1h `access_token`). Save the `refresh_token`.

### 3c. How the app authenticates (refresh-token flow)
```
POST https://accounts.zoho.com/oauth/v2/token
  grant_type=refresh_token
  client_id=<CLIENT_ID>
  client_secret=<CLIENT_SECRET>
  refresh_token=<REFRESH_TOKEN>
→ { "access_token": "...", "expires_in": 3600, ... }
```
Cache the `access_token` (~1h), refresh on expiry, and send every Desk call with:
`Authorization: Zoho-oauthtoken <access_token>` + `orgId: 854214247`.

### 3d. Security
- client_secret + refresh_token live **server-side only** (env vars / secret manager) — never in browser, git, or client code.
- Scoped to **Desk.settings** only → the app **cannot** read/write tickets, contacts, or other modules. Good blast-radius limit.
- Refresh token is long-lived but **revocable** in the API Console if leaked; rotate periodically. Zoho caps refresh tokens per client (~20) — don't regenerate carelessly.

## 4. The operation — manage picklist values (read-modify-write, LAYOUT-scoped)
Picklist values on this org are managed **per layout** (verified 2026-07-06 — the layout-scoped endpoint is the one that works). You always send the **full** `allowedValues` list — there is no add-one / remove-one endpoint.

**Read current values:**
```
GET /api/v1/layouts/999149000010342586/fields/{fieldId}
Headers: orgId, Authorization
→ field object incl. "allowedValues": ["-None-", ...]
```
(or GET the whole layout `/api/v1/layouts/999149000010342586` and read the field.)

**Update (create / rename / delete a value = replace the whole list):**
```
PATCH /api/v1/layouts/999149000010342586/fields/{fieldId}?orgId=854214247&isMandatory=false
Headers: orgId, Authorization, Content-Type: application/json
Body: {
  "allowedValues": ["-None-", "Value A", "Value B", ...],
  "defaultValue":  "-None-",
  "sortBy":        "userDefined",
  "isMandatory":   false
}
```
- **All four body fields are required** (allowedValues, defaultValue, sortBy, isMandatory) — re-supply the unchanged ones. `isMandatory` is also sent as a query param.
- Keep `-None-` first (default placeholder). Create = append; Rename = change the string; Delete = omit — then PATCH the whole array.
- Round-trip verified: Application → `["-None-","processing-ms"]`, Environment → `["-None-","UAT"]`.

## 5. Guardrails (design the app around these)
1. **Serialize writes.** Because each change rewrites the whole array, concurrent edits clobber each other — use a queue/lock per field.
2. **Deleting a value that's in use blanks it on existing tickets.** Before removing a value, check usage (`GET /api/v1/tickets/search?customField1=cf_application:<value>` or a report); prefer **soft-deprecate** (keep/rename) over hard-delete, or delete only after confirming zero usage.
3. **Layout-scoped.** These value lists belong to the **DevOps Request** layout (`999149000010342586`). If a field is ever added to another layout, that layout keeps its own list — update each layout you care about (today it's only DevOps Request).
4. **Value-name rules:** no special chars / emojis (same restriction as status names). Keep names ≤ ~120 chars.
5. **Rate limits.** Batch the final list; don't PATCH on every keystroke.
6. **Log every change** (before → after list + who/when) so you can roll back.
7. **One source of truth.** Let the app own the master list and push one-way to Zoho; run a periodic reconcile (GET) to detect any manual UI edits (drift).

## 6. How to start
1. **Tag** — DONE: stays **free text** (user input, not app-managed).
2. Owner generates the zagent OAuth refresh token with the scopes in §3.
3. **Seed** — DONE (2026-07-06): Application = `["-None-","processing-ms"]`, Environment = `["-None-","UAT"]`; layout-scoped round-trip proven.
4. App implements the read-modify-write in §4 with the §5 guardrails.

## 7. Building the integration — end-to-end reference (for the app developer)
All examples use the `.com` DC and the **DevOps Request** layout `999149000010342586`. Replace `<...>` with the credentials from §3b. Never hard-code secrets — read them from env vars / a secret manager.

Field IDs you'll target:
- **Application** → `999149000010343250`
- **Environment** → `999149000010343580`

### Step 1 — Get an access token (from the refresh token)
```
curl -X POST "https://accounts.zoho.com/oauth/v2/token" \
  -d "grant_type=refresh_token" \
  -d "client_id=<CLIENT_ID>" \
  -d "client_secret=<CLIENT_SECRET>" \
  -d "refresh_token=<REFRESH_TOKEN>"
```
Response:
```
{ "access_token": "1000.xxxx", "expires_in": 3600, "token_type": "Bearer", "api_domain": "https://www.zohoapis.com" }
```
Cache the `access_token` (~55 min); refresh on expiry or on a `401`.

### Step 2 — Read the field's current values (layout-scoped)
GET the whole layout and read the target field from its sections (proven path):
```
curl "https://desk.zoho.com/api/v1/layouts/999149000010342586" \
  -H "orgId: 854214247" \
  -H "Authorization: Zoho-oauthtoken <ACCESS_TOKEN>"
```
Find the field by `id`/`apiName` in `sections[].fields[]` — e.g. Application:
```
{ "apiName": "cf_application", "type": "Picklist",
  "allowedValues": ["-None-","processing-ms"],
  "defaultValue": "-None-", "sortBy": "userDefined", "isMandatory": false }
```

### Step 3 — Write the new value list (create / rename / delete = replace the whole list)
Example — add `issuing-ms` to Application:
```
curl -X PATCH "https://desk.zoho.com/api/v1/layouts/999149000010342586/fields/999149000010343250?orgId=854214247&isMandatory=false" \
  -H "orgId: 854214247" \
  -H "Authorization: Zoho-oauthtoken <ACCESS_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{ "allowedValues": ["-None-","processing-ms","issuing-ms"], "defaultValue": "-None-", "sortBy": "userDefined", "isMandatory": false }'
```
- **Create** = append an entry · **Rename** = change the string in place · **Delete** = omit the entry. Always send the **whole** `allowedValues` array plus the other three body fields.
- Keep `-None-` as the first entry.

### Recommended app flow
1. The app owns the master list of Applications / Environments (source of truth).
2. On any change: get token (Step 1, cached) → GET current list (Step 2) → compute the new list → PATCH (Step 3).
3. **Serialize** writes per field — every PATCH replaces the whole array, so concurrent writers clobber each other.
4. On **delete**, confirm the value isn't in use on existing tickets first (or soft-deprecate) — deleting an in-use value blanks it on those tickets.
5. Log before → after for each change (rollback + audit).
6. Periodically GET and reconcile to detect any manual edits made in the Zoho UI (drift).

### Error handling
| HTTP | errorCode / meaning | What to do |
|---|---|---|
| 401 | `INVALID_OAUTHTOKEN` — access token expired | refresh via Step 1, retry once |
| 429 | rate limit exceeded | exponential backoff, then retry |
| 422 | `INVALID_DATA` — duplicate / special char / bad value | fix the value; don't blind-retry |
| 403 | insufficient scope/permission | verify zagent token scopes = `Desk.settings.READ` + `Desk.settings.UPDATE` |
